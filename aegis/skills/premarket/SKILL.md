# PROCESS: PREMARKET — THE JUDGEMENT HALF (weekdays; plan ready 16:00 SGT, PM approval by 21:00 — RB:schedule)
**Desk sequence (D-26/D-32):** the Chief adopts **Research** (steps 4–9: held read, swarm, tally, event filter, weather, deliberation) → **Risk** (step 10 sizing + gates) → **PM approval** (step 11) → **Execution** (step 11 staging requests). Physical move to `orchestration/` = BL-033. Voices work in isolation at step 5. No numbers here — all thresholds are RB: keys.

## THE SPLIT (D-91) — read this before anything else
Premarket is **two processes**, not one, and this file is the **second** of them.

| | `premarket_data` (cheap) | `premarket` (this file, expensive) |
|---|---|---|
| What it does | fetches today's AQE export, proves it complete + fresh, builds the universe, refreshes the held book / stops / dynCap / metrics, pushes, stamps | spawns the voices, tallies, funnels, deliberates, assembles the plan, takes PM approval |
| Model tier | RB:model_tiers.control — deterministic tools only | RB:model_tiers.judgment for every step that thinks |
| Spawns agents | **none** | the full swarm + one committee-desk |
| Prerequisite | post-market stamped ok | post-market **and** an ok `premarket_data` stamp dated today **and** today's export on disk |

The economic point of the split is that the data work is worth a cheap session and the deliberation is worth an expensive one, and **an expensive session must never be spent discovering that the data is not there.** Step 1 is the whole enforcement of that.

**Nothing in this file fires anything, and nothing fires this file automatically.** No scheduled task exists for either half. Both are started by hand, in order, by the PM or by a session the PM is driving. Where this file says "the data half already ran," that means *someone ran it* — step 1 is how you find out whether they did.

**Model note (D-16):** you, the orchestrator running this skill, are control plane — RB:model_tiers.control. Your job is sequencing, tool calls, and contract validation, never analysis. Every step that needs real judgment (the swarm at step 5, deliberation at step 9) is delegated to a pinned judgment-tier agent — RB:model_tiers.judgment, baked into that agent's own compiled file. Don't reason hard here; spawn, validate, move on.

**Step numbering is deliberately preserved.** Steps 2 and 3 moved wholesale to `premarket_data` and are kept here as pointers rather than deleted, because steps 5 through 12 cross-reference each other by number in a dozen places and silently renumbering them would break every one of those references.

0. **Preflight — the token check already happened, this is the re-check (D-49).** Run `tools/preflight.py`. The HARD stop on a missing `GITHUB_PAT` belongs to the data half, which refuses to start without one because a pushed export is its only deliverable — so if you are running at all, the token was present when that half ran. What this step establishes is whether it still is. This half's own writes — `committee.json`, the pipeline ledger, the alert list, the plan — are exactly as session-local as the export was, and a fresh checkout tomorrow will not have them unless they are pushed. A missing token HERE does **not** stand the phase down: the committee's work is still worth doing and the PM still gets a plan on the phone. It means today's committee record and alert list reach this session's disk only. Say that plainly in the run outcome (step 12) rather than reporting a clean run. Page the PM to paste it into `config/.env` (the tool prints the exact one-liner). Never fabricate a token.
1. **Confirm the gate FOR THIS HALF — `--for premarket_build` (D-83/D-91).** Run `python3 tools/phase_gate.py check --for premarket_build --json` and read the exit code. **0 = READY → proceed to step 4.** Anything else → **STOP HERE and stand down**, paging with the check's own `reasons` verbatim: 1 (NOT_READY — post-market, today's export, or the data half is merely late) or 2 (BLOCKED — something upstream ran and failed).
   **The `--for` is not optional and not cosmetic.** The two halves have different prerequisites, so one gate answer for both was wrong in a way that mattered. The data half is the process that FETCHES the export, so gating it on the export already being on disk was a deadlock — nothing could ever fetch it — and it is therefore checked against post-market only. This half is checked against all three: post-market stamped ok, today's export present and dated today, AND a `premarket_data` stamp dated today with status `ok`. **Running this check without `--for` silently takes the data half's weaker gate**, which would let the swarm start on an export nobody fetched. If you are reading an exit code you did not pass `--for premarket_build` to obtain, you have not run this step.
   **A `fail` stamp from the data half is BLOCKED, never retry-later.** The cheap half tried and could not produce the data; spinning up eleven judgment-tier voices and a committee-desk on top of that is spending the expensive session on nothing, which is the single outcome this split exists to prevent. The fix is to re-run `premarket_data`, not to re-run this.
   **Do not re-derive freshness from file mtimes, do not eyeball the export date, do not proceed on a partial** — one command, one exit code. The full RB:data_sources.staleness rule is implemented inside the tool; a second copy of it here is exactly the drift this decision removes.
2. **Universe build — MOVED to `premarket_data` (D-81/D-91).** `data/sod/DATE/universe.json` already exists: built by the data half from today's export, schema-enforced against `contracts/universe.schema.json`, trimmed to the consumed field set, carrying its `near_misses` list (D-37 — names just below the alert floor, surfaced in the plan so the committee/PM can revive one, never a silent early cut), and pushed. **Do not rebuild it here.** READ it, and read it as a contract: it must validate, and it must carry the full data taxonomy step 5 requires (the mandatory field list lives in step 5 — check it there, not from memory). If the file is absent, or present but thin, **that is not a thing to quietly fix by re-running the builder** — it means the data half's stamp is claiming something it did not deliver, which is a finding about the pipeline, not a hiccup in this session. Stand down and page with the specific missing field named. **The AQE daily export IS the fully-scored universe (D-66); FMP feeds AQE upstream, so the kernel does NOT re-screen FMP** — `tools/universe_screen.py` is retired to a standalone FMP tool and is on neither half's path.
3. **AQE pull — MOVED to `premarket_data` (D-66/D-70/D-91).** `output/aqe_daily_export.json` is on disk: pulled from the Drive "AQE" folder with the bounded retry ladder, schema-validated against `contracts/aqe_export.schema.json`, tripwire-checked, coverage-checked for completeness and freshness by `tools/aqe_coverage.py`, and pushed to GitHub so it survives the hop between sessions. Step 1's gate is the proof of all of that. **Do not re-pull it, do not re-validate it, do not run `tools/tripwires.py` again** — a second copy of that logic here is precisely the drift the split removes, and a tripwire that BLOCKS on the second run but not the first is an incident report about the tool, not about the market. Read the export directly wherever you need the untrimmed record: step 5's taxonomy, step 6b's funnel, step 10's brackets. If the data half's coverage report carried DEGRADED lines, they travel with you into step 4 and into the plan headline — a run built on partial data is still a run, but the PM is told which part was partial.
4. **Held book FIRST — exits before entries (D-33). THE ARITHMETIC IS ALREADY DONE; THE JUDGEMENT IS NOT.** The data half has already, this morning, off today's export: merged each held name's `aqe_snapshot` + `aqe_snapshot_as_of` (reading BOTH `daily_list` and `held_positions`, so a held name that did not independently make the scored longlist is still refreshed — D-91), recomputed every trailing stop as a mechanical FLOOR (breakeven→structure ratchet, never lowers) off the `bracket` that refresh wrote into each snapshot, written each new floor into `stop_reference` via `held_book_refresh.py stop-update` and recomputed `stop_match` against the broker's live stop, refreshed dynCap via `dyncap_ledger.py update` (allocation + realised + unrealised = current Aegis equity, so today's sizes are against what is actually held and de-size in drawdown), recomputed `journal.metrics` via `portfolio_metrics.py`, and PUSHED all of it.
   **Do not re-run any of that here.** This is not belt-and-braces, it is a correctness problem: the second pass would compute against a journal the first pass already mutated, and the trailing-stop floor in particular must be computed once per day from one export or the ratchet stops being reproducible. Trailing stops are recomputed in exactly one place in this system (D-84), and that place is now the data half.
   **What this step does is READ that state and put judgement on it.** Load the held book from the **Aegis journal file** (`data/journal/aegis_journal_YYYY-MM-DD.json`, D-84 — the sole book of record; the old separate Drive PTJ copy is retired), the one source already filtered to the AEGIS sub-fund (D-17/D-21) — NOT the raw broker account, and NOT the AQE export's `held_positions` block, which is not the Aegis book and carries null price/stop/exposure on every row by design (it mismatched the live account 18 Jul — BL-024). Read alongside it: each position's `stop_reference` and `stop_match` (a MISMATCH here is normal — the broker order usually has not been staged yet — flagged in `review_flags`, never a reason to stop), the refreshed `dyncap`, and `metrics.sector_concentration_pct` against RB:risk.gates.sector_exposure_pct_of_dyncap. From these the Chief adopts **Risk**, identifies rotation candidates, and establishes the capital actually available for new sizing. **Read `review_flags` and carry them into the plan** — a name flagged `not_in_todays_export` is being risk-managed off a structure that did not move today, and the committee must know that before it says RUN. A `sector_concentration_pct` that resolves entirely to one UNKNOWN bucket is a regression, not a breach: say so rather than reporting a gate reading off it.
   The held JUDGMENT — RUN / TAKE-PARTIAL / TIGHTEN / EXIT per name, from price-vs-ATR-range + structural levels + runner-vs-weakening — is the **committee's**, produced at step 9 (D-34); step 10 combines the committee read with the mechanical floor so the **PM decides partial-vs-run**. That division is the clearest illustration of why the split exists: the floor is arithmetic and ran an hour ago on a cheap session; whether to take the partial is judgement and runs here.
   **The hedge assessment runs HERE, not in the data half** — its Phase 1 crosses the coverage matrix with SRM grades and the macro posture, which is judgement, not arithmetic (BL-007, wired 18 Jul). Phase 1 — coverage matrix from the AQE `held_book` (beta-adjusted exposure, loss-per-1%-gap, gap scenarios) crossed with SRM grades and the macro posture, against the current hedge record in the journal. **That record is now REAL, and this is where its Greeks get attached (D-89/D-90).** Post-market derives `journal.hedge` from the confirmed option legs it pulls from both brokers, so Phase 1 finally reads a structure that actually exists instead of the permanent null it used to read — the reason this phase concluded "no hedge on record" every single morning while Phase 2 proposed a fresh structure over one the book already held. Greeks and IV are deliberately NOT in that record: they are analytics, not book-of-record data, and neither broker serves them at contract level. **Pull them HERE, at the point of use, for the hedge legs only — Alpaca, the sole Greeks/chain source, 15-minute delayed (Charter §0.5).** Stamp `greeks_as_of` on the legs so the delay is a visible field rather than an assumption. **If that pull fails or IV comes back empty, the coverage math still runs** on `hedge_engine`'s documented 0.20 default — but SAY SO on the hedge line in the plan, because a coverage number computed on an assumed vol is not the same claim as one computed on a measured vol, and the PM sizes differently on the two. **Interrogate the beta input before trusting the conclusion.** The coverage matrix sizes off `beta_adj_exposure_usd`, and a 30-day beta window prints negative for a name that is merely uncorrelated over that window as readily as for one that is genuinely inverse. A book showing single-digit-percent beta-adjusted exposure on full gross is a number to question, not a conclusion to act on — "no hedge needed" reached that way is a data artefact wearing a verdict's clothes. If the data half's coverage report flagged the beta window, quote the flag on the hedge line. Phase 2 — only if coverage is short for the posture: `tools/calculators/hedge_engine.py` generates three candidate put-spread structures (chain via `alpaca_client.py`, spot via Tiger) scored by coverage-to-cost; the recommended structure enters the plan's hedge block. Skip rule retained: `position_count < 4` → skip and log. A hedge order is order-shaped like any other: it reaches the PM as a plan item and any preview routes through the staging-gatekeeper.
5. **Independent nominations — THE SWARM (explicit mechanics).** One SEPARATE subagent invocation per compiled agent file in `agents/voice-*.md` — the active roster (**11 with the Elder lens, D-51**), never many roles in one context (RB:committee.anti_anchoring). **THE SWARM ALWAYS RUNS — a portfolio breach NEVER skips it (BL-043 / D-65, PM-approved).** A portfolio hard-gate breach (RB:risk.breach_rule — e.g. sector concentration over the hard gate at RB:risk.gates.sector_exposure_pct_of_dyncap) caps ONLY what may ADVANCE at committee (steps 9–10); it never skips, delays, or shrinks the swarm. Analysis is not an order: the 11 voices evaluate the full universe on every premarket regardless of book state, and the breach constrains verdicts, not thinking. An empty Nomination Ledger caused by a skipped swarm is an INVALID run (the auditor fails it) — the 18–20 Jul empty-Ledger sessions traced to exactly this deviation, and it must not recur. **DATA TAXONOMY IS MANDATORY (D-53 — the swarm may not run data-starved).** The `universe.json` handed to the voices MUST carry, per name, the full union of the voice data menus (`VOICE_MENUS` in the build) sourced verbatim from the AQE `daily_list` record — the sub-component taxonomy: `elder_5d`, `elder_pattern`, `mp_state`, `mp_accel_state`, `structure_shift`, `sma_distance_pct`, `rvol`, `rs_spy_20d`, `rs_leadership`, `ma_20/50/100/200`, `atr_14d`, the full `bracket` block (incl. `valid`, `atr_fallback_stop`, targets, `rr*`), `lens`/`lens_positive`, `sector_trend_state`, `beta_30d`, and the composites. **A universe reduced to a thin score summary is an INVALID run — the auditor fails it, and this half STANDS DOWN at step 2 rather than rebuilding it (D-91).** The builder belongs to the data half now; a session that quietly rebuilds its own inputs would paper over the fact that the data half stamped `ok` on something thin, and that fact is the thing worth knowing. A voice may still only READ its own menu (D-29), but the field must be PRESENT to be read; the 20 Jul dry run fed a stripped 8-field projection and the voices nominated half-blind (they said so) — that must never recur. Per voice: **Claude** — spawn via the Agent/Task tool, prompt = that agent file + the taxonomy-complete universe file + the injected `tools/voice_memory.py render <voice>` block (rolling stats, open picks, STANDING LESSONS D-14; the voice states which lesson applies before nominating), tools disabled; **Kimi** — spawn its subagent definition from `agents/`. Each subagent is a FRESH context: no session, no other voices, no tally. All run in parallel; each returns `nomination.json` (contracts/nomination.schema.json); the orchestrator schema-validates each on receipt. Fewer than the menu-cap with `shortfall_reason` is a valid outcome. **SELF-HEAL ON DECLARED GAPS (D-55 — the agentic-loop principle, no sloppiness).** After receipt, the Chief collects every voice's `data_gaps[]`. For each gap it ROUTES by source per `contracts/field_dictionary.json`: a market/technical field (`ma_20/50/100/200`, `atr_14d`, `rvol`, `rs_spy_20d`, `sma_distance_pct`, `close`, `beta_30d` — anything derivable from prices) is sourced from the **FMP MCP**; an AQE engine-computed field (`sc_momentum`, `structure`, `mp/mp_state`, `elder/elder_5d`, `lens*`, `bracket`, `energy`, `flow`) is sourced by **triggering an AQE re-export** (or reading the fuller AQE record already on disk). The Chief patches the universe record and RE-RUNS the affected voice(s) on the repaired data. Only if a field is genuinely unavailable from both (declared, not guessed) does the name proceed with the gap noted. A voice that declared a gap and was NOT healed before tally is a broken loop — the auditor flags it. This is data-driven design with self-heal: the voice's job is to READ and DECLARE, the Chief's job is to SOURCE; neither invents.
6. **Tally & tier.** Count nominations across every returned voice file — the roster as it actually ran at step 5, not a hardcoded seat count (lens seat counts equally, D-5; empty seats from a voice that failed twice are shown as empty, never backfilled); stamp `price_at_nomination` into every nomination from the universe file; **also stamp `field_values` (D-20): for each nomination, look up every name in its `fields_cited` in the universe file and record the actual value — this is a deterministic dictionary lookup, no model judgement, and it is what turns each idea from a one-line assertion into a data anchor the PM can inspect.** **Also stamp `quality_flags` (D-39): run `tools/quality_flags.py derive` on each deliberation-set and held name's full AQE record and attach the fired STRENGTH/CAUTION flags (with their source values) — deterministic (law 4), the voices' own restored evaluation vocabulary, SOFT (never a tier/gate change). These travel into the deliberation packet and the plan render.** **DATA BOARD — attach to the consensus tally EVERY DAY (D-60, PM ask).** Immediately after the tally, run `tools/subscore_board.py --universe data/sod/DATE/universe.json --consensus <tally> --out data/sod/DATE/subscore_board.json` — a DETERMINISTIC (law 4, no models, no tokens) view that ranks the SAME universe three ways off the raw AQE sub-scores: (1) detect lens alone (lens_positive), (2) each voice alone (its own menu fields), (3) a data-only TIERING by agreement across three orthogonal axes (voice sub-score breadth · detect strength · elder force). It is a TRANSPARENCY/decision-support attachment, NEVER a gate (D-4/D-52 spirit) — it ranks, it never removes or advances. The board renders beside the consensus picks (step 10) with the board↔consensus divergence called out: names where pure data and the voted tally AGREE (highest-confidence), DATA-ONLY (board Tier-1 the voices under-nominated), and CONSENSUS-ONLY (voted but not data-Tier-1) — that divergence is where the sector/bellwether judgment earns its keep. **PIPELINE CARRY-OVER — the ledger's daily half comes back in HERE (D-83).** Run `python3 tools/pipeline_ledger.py active --classification daily_reconsider --json`. Every active row is a name a previous committee explicitly asked to keep alive. Each one joins the deliberation set as a **CARRY-OVER entry** carrying its `case_snapshot` verbatim — the case that committee made — plus its `origin_date` so today's committee can see how long it has been waiting. **It is re-scored fresh from today's universe file like any other candidate; the snapshot is context, never a score and never a shortcut past the threshold below.** A carry-over whose ticker is NOT in today's universe cannot be deliberated on data — it goes to the watch table with its snapshot and a "not in today's universe" note, and stays in the ledger until its TTL. Carry-overs do not consume a nomination slot and do not inflate `nomination_count`. Deliberation set = RB:committee.deliberation_threshold — ≥2 nominations OR lens-top OR **a single voice at conviction ≥ RB:committee.solo_high_conviction_min (D-37: a strong lone signal is NOT relegated)** OR **an active `daily_reconsider` carry-over**; everything else → ranked watch table (each watch row keeps its nomination_count, nominating voices, and 2–3 anchor values — never a bare ticker). ALL nominations → Nomination Ledger.
6b. **CONVICTION FUNNEL — the three-axis daily shortlist (D-78, PM: "data driven, lens and consensus driven… concise summary highlighting contradictory or positive overlaps… always start from approx 10–15 names to filter down into a high conviction plan").** After the tally and the event filter, run `tools/conviction_funnel.py build --tally data/sod/DATE/tally.json --export output/aqe_daily_export.json --event-blocked <event-driven names> --out data/sod/DATE/conviction_funnel.json` — DETERMINISTIC (law 4, no model). It grades every nominated name S/M/W on three axes, but in a DELIBERATE ORDER (D-79, PM: "data but lens first before we anchor on voices advisory"): **DATA** (the 8-lane casting mat, D-77 — momentum-arrival depth) and **LENS** (the 6-lens detect count) are the PRIMARY, mechanical axes; **CONSENSUS** (voices: nomination count + avg conviction) is an ADVISORY overlay, never the entry ticket. It produces: (1) a **SHORTLIST of ~10–15 names whose entry is MECHANICAL — DATA strong OR LENS strong** — ranked by lanes+detect first (votes only a tiebreak), each tagged **TRIPLE** (data+lens+voices all agree — highest), **CONFIRMED** (data/lens-led AND the swarm backed it), or **DATA_LED** (data/lens-led but voices advisory-silent — the swarm under-nominated it, promoted into the shortlist anyway because data leads). This is the high-conviction start-point for deep deliberation. (2) **CONTRADICTIONS TO RESOLVE** — `consensus_only`: names VOTED well (≥ RB:conviction_funnel.cons_strong_votes) but where DATA+LENS do NOT confirm (e.g. DINO 4 votes/2 lanes, and even the top-headline-momentum UNP/CSX 4 votes/3 lanes/0 lens on 21 Jul) → the voices are advisory only here, so the committee must explicitly rule fresh-or-stale, run or drop. (The former 'data-strong-but-under-nominated missed runner' set is now PROMOTED into the shortlist as DATA_LED rather than sidelined — data leads.) This is TRANSPARENCY/decision-support, never a gate (D-4/D-52) — it focuses and frames deliberation, it never removes or advances a name on its own. The concise `summary` string is surfaced in the plan render. **The committee (step 9) deliberates the shortlist AND must explicitly RESOLVE each contradiction (run or drop, with reason) — a contradiction left unaddressed is an incomplete deliberation.** Complements the D-60 data board (which stays); the funnel is the momentum-lane-aware convergence view that drives the ~10–15 name start-point.

8. **Macro & SRM weather + BELLWETHER letters.** Druckenmiller macro brief + SRM read presented as context (RB:srm.role) alongside the deliberation set — after nominations, never before. **Weekly bellwether inputs — the CS Weekly Market Overview and the Crown Macro Letter (PM-supplied) — travel with this context (D-59). A quote must be apt or omitted, never decorative. These are the market's bellwether view, not an oracle: cite as corroboration or tension, PM decides.
9. **Deliberation — spawned, not inline (D-16); Risk sits at the table (D-36).** **SELECTION DOCTRINE (LOCKED, D-80): DATA leads · LENS seconds · VOICES corroborate or challenge → consensus for HIGH CONVICTION.** The committee deliberates the step-6b DATA+LENS-led shortlist and the flagged contradictions: for each name the voices either CORROBORATE (add their case + conviction), stay silent (mechanical-only, note it), or CHALLENGE (dissent / bear case, or defend a voted name the mechanicals didn't confirm). HIGH CONVICTION = mechanical confirmation (data/lens) AND voice corroboration; a mechanically-strong name the voices challenge, or a voted name the mechanicals don't confirm, must be explicitly RESOLVED (run or drop, with reason), never auto-advanced. Voices corroborate or challenge — they never carry a name on votes alone. **Historical-store reconcile FIRST (D-40 — self-heal, before anything anchors on it).** The orchestrator runs `tools/historical_store.py check --list <deliberation-set + held book>`; for every name in `seed_needed` (missing, or stale past the last completed month) it pulls that name's daily history via the FMP MCP (`historical-price-eod-full`, ~6y) and runs `tools/historical_store.py seed <TICKER> --bars <file>` — a deterministic data-plane tool call, NO agent (anti-lasagna), FMP the only source (matches the DoR mandate). A name with < 12 months is recorded `deferred_too_new` and skipped on the daily pass (re-checked monthly via `--with-deferred`), never faked. So no name reaches committee/Risk un-anchored. Primary maintenance of the store is AQE's daily pipeline (Engineering & Change desk, D-40/BL-042); this step is the kernel's safety net. Then the orchestrator has **Risk** produce its anchored read per candidate + held name (ATR/structural/macro/portfolio-fit, sector-exposure impact, sizing-conviction scenarios via `book_sim`, and the post-add **parametric portfolio VaR** via `tools/calculators/var_parametric.py` — single-factor 95% 1-month, D-42, for the VaR gate) — Risk is a VOICE anchored on data, not a downstream calculator. Then it assembles the deliberation-set packet (every nominating voice's case verbatim INCLUDING its `field_values` and the stamped `quality_flags` (D-39), held-book lines, brackets, SRM weather, macro brief, live account snapshot + the Risk lens read) and spawns ONE isolated `agents/committee-desk.md` agent — judgment tier, never run inside the orchestrator's own context. It returns new-idea verdicts (ADVANCE / HOLD-FOR-CONDITIONS / PASS + conviction + mandatory bear case + dissent) AND **`held_verdicts` (D-34): a full deliberation of each HELD position — RUN / TAKE-PARTIAL / TIGHTEN / EXIT from price-vs-ATR-range, structural levels, and runner-vs-weakening momentum — plus a sector-concentration flag**, each with **`data_anchors` (D-20): the decisive field values behind the verdict** → validated against `contracts/committee.schema.json` → `data/sod/DATE/committee.json` (SOD shelf — BL-012). **File the Pipeline Ledger HERE, immediately (D-83/D-84 — moved from post-market, PM: "we file immediately after premarket... it eventually feeds into intraday monitoring, things on list but missed during premarket").** The moment `committee.json` is written, run `tools/pipeline_ledger.py persist --committee data/sod/DATE/committee.json --date DATE`. This is filing only, no new judgement — the committee already decided `ledger_proposal` per verdict at the moment above; this just writes it to disk. Filing here (not waiting for tonight's post-market) is what lets a `trigger_silent` name join step 10's List P THE SAME DAY, so the market-hours sweep can watch it that same afternoon instead of a full session late. If a portfolio risk gate is breached and unresolved, committee-desk verdicts no ADVANCE at all — that fact leads the plan headline at step 10, same as a stand-down.
9a. **Reactive/off-cycle deliberation — sector-sleeve apples-to-apples.** Any candidate sent to committee OUTSIDE the once-daily swarm cadence (a PM ad hoc request, a live catalyst, a re-look after a thin-conviction result) is NEVER deliberated in isolation. The orchestrator first pulls every OTHER verdict already on record for that name's sector/sleeve from the day's `committee.json` (ADVANCE, HOLD-FOR-CONDITIONS, AND PASS — dump the full `verdicts[]` array, never a ticker-filtered grep; a partial read here (checking only the requested tickers) produced an incomplete picture once and must not recur) and hands the committee-desk spawn the full sleeve side by side. The verdict on the new candidate must say explicitly whether it is ADDITIVE (fills a gap the sleeve doesn't already cover) or REDUNDANT (a same-thesis name where a stronger corroborated case already occupies the slot) — "technically fine" is not "worth a second slot." **Live-catalyst re-contextualization:** when a candidate's case rests on a fresh real-world event (a geopolitical shock, a surprise data print, a Houthi-blockade-style catalyst), verify the event actually happened and is still live via WebSearch before treating it as an input — then re-read the name's static metrics (rvol, sc_momentum, structure) against the ACTUAL live tape, not the pre-catalyst snapshot; a metric computed before the catalyst broke is stale context, not current signal.
9b. **Capital/quality separation is absolute — PM standing ruling: "You shouldn't size or pick trades based on my capital. That is my call to leverage or not based on quality of the trade idea."** The committee-desk verdict (ADVANCE / HOLD-FOR-CONDITIONS / PASS) is decided ONLY on trade-quality grounds — framework case, bracket, risk lens, quality flags. ## ON FAILURE (RB:exceptions — the ladder governs; every event writes an exception record to data/sod/DATE/exceptions/)
- **Step 1's gate is not READY** (post-market missing/failed, today's export absent, or no ok `premarket_data` stamp for today) → **STAND DOWN before spawning anything**: no swarm, no committee, no plan, no alerts, nothing armed; PAGE with the gate's own reasons verbatim. This is the cheapest possible failure and it is deliberately the first thing that can happen. Held book stays protected by broker-side stops. Record the day as stood-down; post-market still runs.
- **The universe file is absent, fails its schema, or is missing taxonomy fields** → STAND DOWN at step 2 and PAGE with the missing field named. Do NOT rebuild it here and do NOT spawn the swarm on a thin universe — a data-starved voice nominates half-blind and says so, which is a wasted expensive session dressed up as a run.
- A voice returns nothing/invalid → **first check the failure text against `tools/self_heal.py`'s `detect_usage_limit()` (D-72).** A match (a session/rate/weekly-cap signature, not a content problem) is a DIFFERENT failure from a voice simply nominating badly: run `tools/self_heal.py premarket --failure usage_limit` (capacity class, no auto-retry — retrying now just re-hits the same ceiling) and PAGE with the D-72 manual fix (wait for the account's usage window to reset, then "rerun premarket") — this is a Claude Max-plan capacity ceiling, not a data or voice-quality issue, and must not be mislabeled INCOMPLETE. No match → the ordinary path: re-spawn ONCE → still bad: proceed with the rest (minimum 8), tally shows the empty seats, auditor marks INCOMPLETE; morning summary. The SAME usage_limit check applies to the committee-desk spawn at step 9 (a single opus call, same ceiling risk) — a failure there pages the same way rather than being treated as "deliberation cannot complete" below.
- Hedge tools fail → plan ships WITHOUT the hedge block, flagged in the headline; morning summary.
- Deliberation cannot complete → no name gets ADVANCE (watch-table only); held actions still ship; morning summary.
- Plan fails its contract at assembly → do NOT deliver a broken plan; STAND DOWN + PAGE.
